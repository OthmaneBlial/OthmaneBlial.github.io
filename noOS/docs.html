What noOS is

noOS is an experimental x86 operating system. A BIOS loads its boot sector, which loads a second stage and then a protected mode Assembly kernel. It runs directly on the virtual hardware QEMU provides.

All code executed by noOS is NASM Assembly. Python and Make build the disk image and run tests on the host; neither is part of the operating system runtime. There is no libc or host operating system inside the guest.

Supported target: QEMU’s legacy BIOS pc machine with VGA text mode, the legacy PIC, PIT, COM1 serial output, and a PS/2 keyboard. Physical hardware and UEFI boot are unverified.

Boot & architecture

BIOS → first stage

Loads the first sector at 0x7C00; the loader preserves the BIOS boot drive.

boot/stage1.asm
16-BIT REAL MODE
First stage → second stage

Reads the second stage from the raw disk image and transfers control to 0x8000.

boot/stage2.asm
BIOS DISK SERVICES
Second stage → protected mode

Preserves the E820 map, loads the kernel, checks A20, installs a GDT, sets CR0.PE, and makes a far jump.

boot/gdt.asm
FLAT SEGMENTATION
Protected mode → kernel

Initializes segment registers and a stack, then enters the kernel at 0x10000.

kernel/entry.asm
32-BIT KERNEL

Kernel initialization

kernel/main.asm initializes and checks the VGA terminal, IDT, PIC, physical allocator, heap, and paging. It then installs the PS/2 keyboard, detects the CPU, configures the PIT, enables interrupts, checks tick-based delay, and starts the shell.

Hardware ownership

The kernel writes its VGA terminal through 0xB8000. The PS/2 driver receives keyboard events through IRQ1 after the PIC is remapped and the IDT installed. The PIT drives IRQ0. COM1 serial output exposes boot and diagnostic events to QEMU’s host terminal.

The source modules live in kernel/. The roadmap below records each implementation’s verification status.

Memory & paging

The second stage preserves BIOS E820 records. The kernel validates the map, distinguishes usable from reserved ranges, reserves the first MiB, and allocates complete 4 KiB physical frames from usable RAM below 128 MiB.

Physical frames and heap

The physical allocator tracks eligible, busy, and pinned frames. It handles exhaustion and rejects unaligned, out-of-range, invalid, double, and pinned-frame frees. The 64 KiB heap uses 16-byte aligned allocations, first fit, block splitting, and adjacent free block coalescing.

mem reads the actual E820 usable total, managed usable frames, unavailable frames inside the managed window, allocated/free frames, and heap usage. Detected usable memory above 128 MiB contributes to the E820 total but is outside the allocator’s current management window.

Supervisor paging

The kernel identity maps the first 128 MiB with supervisor-only page tables. The null page is absent, and the VGA page is uncached. CR0 paging and supervisor write protection are enabled. One page directory and 32 page tables occupy 33 pinned frames that cannot be released through the allocator.

This is one kernel address space, with no user mode isolation yet. The mapped window also includes reserved and unavailable addresses; only E820-eligible frames enter the physical free pool. Boot checks validate the kernel, stack, E820, heap, and VGA mappings before paging is enabled.

Line editing

Left and Right move the cursor. Home and End jump within the line. Delete and Backspace remove characters; Escape clears the draft. Tab inserts one space. Up and Down navigate eight history entries while preserving the current draft. Input is bounded to 127 ASCII characters.

Filesystem and user process commands will be documented when their separate implementations are verified.

Timer & CPU

The PIT uses a 1,193,182 Hz input clock and divisor 11,932, producing roughly 100 IRQ0 ticks per second. Both tick and elapsed second counters are 64-bit. Seconds are derived from accumulated PIT input cycles rather than assuming an exactly 100 Hz rate.

The kernel’s tick-based delay uses interrupts and halt while waiting. It rejects disabled interrupts and invalid tick counts. uptime reads the counters; sysinfo also exposes actual keyboard IRQ and dropped-event counts.

CPU initialization first tests CPUID availability, then obtains vendor, family, model, stepping, and feature bits from the virtual CPU. Values displayed by cpu come from that hardware response.

Build & test

Install NASM, QEMU, GNU Make, and Python 3. Build tools run on the host; the result is a raw BIOS disk image that QEMU boots.

BUILD AND BOOT
git clone https://github.com/OthmaneBlial/noOS.git
cd noOS
make
make run
TargetResult
makeAssemble the stages and kernel; build build/noos.img.
make runBoot the image with QEMU, 128 MiB of RAM, and serial output in the host terminal.
make testBuild and run the automated QEMU checks defined in the current checkout.
make debugStart paused with a GDB server at 127.0.0.1:1234.
make sizeReport the current binary sizes.
make cleanRemove generated build output.

The raw image, NASM listing, and binaries are generated locally. Inspect Makefile and tests/ for the exact build and verification commands. A QEMU pass establishes virtual platform behavior; it is not a physical machine test.

What the tests inspect

make test runs QEMU checks for boot, VGA, keyboard, shell, memory, paging, and hardware diagnostics. The memory matrix uses 16, 64, 128, and 256 MiB guests and compares the preserved E820 records with allocator accounting. The 256 MiB case checks that detected memory above the management ceiling stays outside the free pool.

The suite also inspects actual page directory and table entries, supervisor permissions, the absent null page, VGA cache flags, and pinned paging structures. Fault tests deliberately trigger invalid opcode, page fault, general protection, and divide error exceptions. Hardware tests check live PIT counter advancement, CPU data, and keyboard IRQ statistics.

See test_memory.py, test_paging.py, and test_hardware.py for assertions and scope.

GDB debugging

Use x86_64-elf-gdb, or another GDB build with i386 target support. Run make debug in one host terminal; QEMU’s -S option pauses the guest before execution. Connect from a second terminal.

CONNECT TO THE PAUSED GUEST
x86_64-elf-gdb
set architecture i386
target remote 127.0.0.1:1234
hbreak *0x10000
continue
info registers
x/12i $pc

The hardware breakpoint stops at protected mode kernel entry. Flat NASM binaries do not carry ELF debug symbols; build/kernel.lst helps correlate instructions with source. stepi advances one instruction; x/16wx 0xB8000 inspects VGA memory.

Keep the GDB server bound to 127.0.0.1. The debug target already uses this loopback address.

Limits & contributing

noOS is a developing kernel. UEFI, x86-64, physical hardware compatibility, persistent filesystems, scheduling, user mode, and executable loading require their own implementation and evidence. The roadmap distinguishes completed work from planned work.

Keep runtime code in NASM Assembly, validate untrusted input, and include a focused test for nontrivial behavior. Report the exact checkout, QEMU command, observed output, and reproduction steps when filing a bug.

Completed milestones are tested, committed, and pushed to main. Roadmap gates increase only when the implementation is verified. Review the engineering roadmap, inspect the source repository, or open an issue.
